# Phase 4 — release signing and custody plan

**Status:** plan only. **No production signing material has been created,
and none exists in this repository.** Creating the commercial upload key
requires a separate, explicit owner instruction (ADR-010 §5, reaffirmed by
the Checkpoint A review).

## Current state, verified

| Artifact | Signing |
|---|---|
| `aurelius-2.0.0-rc1-debug.apk` | Android Debug certificate — `C=US, O=Android, CN=Android Debug`. Sideload only. |
| `aurelius-2.0.0-rc1.aab` | **Unsigned.** No upload key exists. |
| Repository | No `.jks`, `.keystore`, `.p12`, `.pfx`, `.pem` or `.key` file anywhere. `tools/validate.py` fails the run if one appears, and the candidate gate additionally rejects key material inside a candidate directory. |

Verified by `tools/verify_candidate.py`, which asks `apksigner` rather than
looking for `META-INF/*.RSA` — modern APKs keep the signature block in the
ZIP central directory, so an absent META-INF entry proves nothing.

## What Play actually requires

From `support.google.com/googleplay/android-developer/answer/9842756`,
checked 2026-07-26:

- new apps are enrolled in **Play App Signing** automatically, with
  Google-generated quantum-ready hybrid keys;
- the **app signing key** is held by Google — RSA 4096-bit when
  Google-generated, combined with post-quantum ML-DSA-65;
- the **upload key** is held by the developer — a Java keystore, **RSA
  2048-bit minimum**;
- an upload key **can be reset** if lost; a self-managed app signing key
  **cannot**.

That asymmetry is the whole reason this plan is short: with Play App
Signing, losing our key is recoverable. It is still not something to be
casual about.

## The plan

### 1. Ownership

The commercial signing identity belongs to **AGENOR / xsytrance** as the
Play developer account holder. One person is accountable for it.

### 2. Key purposes, kept separate

| Key | Purpose | Where it lives |
|---|---|---|
| Android debug | local sideload and device testing | the standard `~/.android/debug.keystore`; never committed |
| Upload key | signs bundles uploaded to Play | created offline, stored outside Git; **does not exist yet** |
| App signing key | signs the APKs Play delivers | Google-generated and Google-held; we never possess it |

### 3. Creation procedure (when authorised — not now)

1. On the owner's machine, offline, not in any repository directory.
2. `keytool -genkeypair -v -keystore aurelius-upload.jks -keyalg RSA -keysize 4096 -validity 10000 -alias aurelius-upload`
   — 4096 exceeds the 2048 minimum; validity comfortably outstrips the
   product.
3. A passphrase generated by a password manager, never typed from memory,
   never reused.
4. Record the SHA-256 certificate fingerprint in the owner's password
   manager entry — **not** in this repository.

### 4. Storage, backup and recovery

- Primary: the owner's password manager, as an attached file with the
  passphrase.
- Backup: an encrypted copy on separate offline media held in a different
  physical location.
- **Recovery is verified, not assumed** — restore the backup to a scratch
  machine and sign a throwaway bundle before relying on it. An untested
  backup is not a backup.

### 5. Access control

Least privilege: the owner only. Claude Code and CI do not need it and
must never be given it — CI builds unsigned bundles, and signing is a
deliberate human step.

### 6. Rotation and compromise response

Because Play App Signing holds the app signing key, a compromised **upload**
key is recoverable: revoke it in Play Console, register a new one, continue
publishing. If it happens: rotate immediately, review the release history
for uploads you did not make, and record the incident.

A compromised **app signing** key would be far worse, which is precisely
why Google holds it rather than us.

### 7. Release ceremony

1. Verify the candidate: `tools/verify_candidate.py` reports 0 problems.
2. Verify the tree is clean and the commit is the intended one.
3. Confirm `tools/validate.py` reports no secrets.
4. Sign the bundle with the upload key, on the owner's machine.
5. Record the signed artifact's SHA-256 in the candidate record.
6. Upload.
7. Confirm no key material entered Git, the build log, CI output, a
   screenshot or a report.

### 8. What may and may not be committed

**May:** certificate SHA-256 fingerprints of *public* certificates,
signing *state* descriptions, unsigned artifacts, debug-signed test
artifacts.

**Must never:** any keystore, private key, passphrase, recovery code,
Play Console token, service-account JSON, or a screenshot containing any
of them.

### 9. Disposable validation

The workflow may be rehearsed with a throwaway keystore created **outside
Git** and deleted afterwards. Nothing in Phase 4 required it: the bundle
builds and verifies unsigned, so the packaging path is already proven
without touching key material.

## Open owner decisions

1. Authorisation to create the upload key — **not given**.
2. Which machine and password manager hold it.
3. Who is the fallback if the owner is unavailable.
